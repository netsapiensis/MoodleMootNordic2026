Moodle 5.2 · OpenTelemetry · OpenSearch

What Is Your Moodle Doing?

This presentation shows you how to send Moodle logs and timing data to OpenSearch using OpenTelemetry. In OpenSearch you can run searches to analyse the state of your Moodle site. Moodle 5.2 is the first Moodle version with official OpenTelemetry support. Older versions cannot use this setup.

The slides and the demo files are at https://github.com/netsapiensis/MoodleMootNordic2026, in the folder Moodle-Otel-Opensearch.

The log table

Moodle already logs every event

"Login failed for user 'admin'. Most likely the
 password did not match (error ID '3')."

"The user with id '2' viewed the 'assign' activity
 with course module id '2'."
  • Every click, every login and every failure becomes one row in mdl_logstore_standard_log. That table is in the same database that serves your pages, and it is usually one of the largest tables you have.
  • Moodle's built-in reports, such as Logs and Live logs, use this table.
  • By default Moodle never deletes these rows, so the table grows for as long as the site runs.
The log table
~2 min. The two records are real, copied from the demo site you will see at the end — nothing needs to be invented, Moodle has logged like this for years. Ask the room who has ever read these records anywhere except Moodle's own reports. Then the part where the room nods: anyone who has hosted Moodle at scale has watched logstore_standard_log grow, and has either shortened the retention setting or paid for the table. Name the trade honestly: the history has value, but the database is the wrong place to keep it — it is the most expensive storage in the estate and every report query lands on the production server.

The log table

Questions the core Moodle reports cannot answer

  • How many logins per hour were there this week and last week?
  • Which courses are actually used, and which has nobody opened since term start?
  • What did this one user do, across every course, last month?
  • Are failed logins spiking right now?

In OpenSearch you can answer each of these questions. One more question is why a page was slow. That question gets a short look at the end of this presentation.

The software

OpenTelemetry sends the Moodle data to OpenSearch

OpenTelemetry is a log shipper. It is open source under the Apache 2.0 license. It takes the data that Moodle produces, the events and the timings, and sends it to OpenSearch.

There is no package called OpenTelemetry. The OpenTelemetry project publishes separate programs and libraries. This talk uses these four:

ext‑opentelemetry a PHP extension — hooks into running PHP code without editing it
SDK PHP libraries — turn the Moodle data into records, in memory
exporter a PHP library — encodes the records and sends them over the network
OpenTelemetry Collector a separate service — receives everything, filters it, forwards it to storage

None of them stores data or displays it. That is OpenSearch's job.

https://opentelemetry.io

Setting the scene
~2 min. Say it the plain way first: for this talk OpenTelemetry is a shipper — it takes the data that Moodle produces, the events and the timings, and sends it to OpenSearch. Then what the project publishes, because the room will meet both kinds: the specification defines the record format and the OTLP network protocol; the programs and libraries implement it, one library set per language, PHP among them, plus the collector as a separate program. Then the table: four pieces, installed separately, none of them a package called OpenTelemetry. Land on the last line — nothing here stores or draws — so nobody expects a screen from OpenTelemetry.

The software

OpenSearch stores the events and searches them

OpenSearch is an open-source search engine and document store, forked from Elasticsearch, with a web front end called OpenSearch Dashboards.

What it does

Indexes every event, and every timing, as one document, then answers questions about millions of them in milliseconds. OpenSearch Dashboards draws charts from them. Indexing means every field — duration, task name, file path, line number — is written into a structure built for searching.

Why choose OpenSearch

  • Grows by adding servers. An index is split into shards spread over the nodes of a cluster; a replica of each shard survives a lost node.
  • Fast on large volumes. A search looks up the index instead of scanning every stored document, like the index at the back of a book, so it stays fast as the data grows.
  • Speaks OpenTelemetry. The OpenTelemetry Collector ships an OpenSearch exporter; OpenSearch Dashboards has Trace analytics built in.
  • Retention built in. A policy deletes whole indices on schedule.

https://opensearch.org

Setting the scene
~1 min 30 s. Define indexing properly, because half the room will only know grep. The contrast to draw: grep reads every byte of every file every time; an index is built once at write time so the question is answered without reading the data. That is why "which of my 40 000 cron runs took over 30 seconds last month" is instant here and impossible in a log file. Two more facts they will need: one document per span and per log record, and the indices roll over monthly, which is where retention gets decided. The right-hand card is the case for OpenSearch over a database table or a log file: it grows by adding servers (the docs' own example is a 400 GB index split into 10 shards over 10 nodes), and it is Apache 2.0 with RPM and DEB packages, which the lead-in already covers with "open source". The last two bullets are the reasons it fits this pipeline: the OpenTelemetry Collector already has an OpenSearch exporter, and OpenSearch Dashboards already has the trace screens.

The pipeline · where it all runs

Where does each component run?

The chain
~1 min 30 s. Three statements, in this order. One: components 1 to 4 are not merely on the same server — they are inside the same PHP process, the one that runs Moodle's code. There is no deployment decision to make and nothing to install elsewhere. Two: the collector runs on the Moodle web server too, as a separate service. That is what the walk-through installs: one collector per Moodle server, talking over localhost, so the data never crosses the network on its way to the collector, and port 4318 stays closed. No extra server is needed. The other way is one shared collector on its own host for every web server you run — fewer things to configure and one place to filter personal data — the pattern we run; it needs the endpoint variable pointed at that host and port 4318 open there. Three: OpenSearch is always separate, and it is the one component most of them already have. If asked which to pick: the shared host for a small estate, one per server once traffic is large enough that you want the buffering close to the source. Two glosses to give in passing: OTLP on the arrow is simply the message format, properly defined in part two; and the reason for a relay at all is buffering — PHP hands the data off in a millisecond and gets back to serving the page, and if OpenSearch is slow or down the collector absorbs it instead of the request failing.

These terms appear in the commands and in the searches

The terms
Section runs ~6 min. Say the transition plainly: so far you have seen what the six components are and where they run; nothing is installed yet. Before the commands, four terms, because they appear in the commands, in the collector config and in every search — in Discover's field browser, in the collector's config, in every OpenTelemetry and OpenSearch document they will read afterwards. Four terms, built in order, each needing the one before it. Nobody should leave having nodded at a term they do not own. Do not rush it. Trace and span are deliberately NOT here — they arrive in the look ahead at the end, once the log story is complete.

Term

Log record: one Moodle event stored as one document

When anything happens in Moodle, it emits an event. Shipped to OpenSearch, each event becomes one document.

body     "The user with id '2' viewed the 'assign' activity
          with course module id '2'."
time     2026-08-23T21:30:58Z
service  moodlelms
The terms
~1 min. Anchor it to what they know: this is the same event Moodle already writes to its own log table — the same stream, pointed somewhere better. Nothing is invented, nothing is parsed out of a text file. One event in Moodle, one document in the store.

Term

Attributes: the key = value pairs on a log record

Every record carries a list of key = value pairs, its attributes. OpenSearch stores each one as a searchable field under the prefix attributes. This is the same log record with seven of its seventeen attributes. The body sentence is built from the first three.

body     "The user with id '2' viewed the 'assign' activity
          with course module id '2'."
time     2026-08-23T21:30:58Z
service  moodlelms

attributes.event.data.userid              2        # the user with id '2'
attributes.event.data.objecttable         assign   # the 'assign' activity
attributes.event.data.contextinstanceid   2        # course module id '2'
attributes.event.data.action              viewed
attributes.event.data.eventname           \mod_assign\event\course_module_viewed
attributes.event.data.crud                r
attributes.event.data.courseid            2
The terms
~2 min. Read the first three attribute lines out loud and point at the words of the body sentence they come from: Moodle builds that sentence from userid, objecttable and contextinstanceid. Then the other four, and dwell on crud. Every Moodle event classifies itself as create, read, update or delete, so the value is c, r, u or d. Answer the where question before it is asked: attributes are written in PHP on the Moodle server at the moment the event fires, they ride inside the record over OTLP, and the OpenTelemetry Collector is the one place to add, drop or hash them in transit. That is how personal data gets controlled. Point at the attributes. prefix on the four lines: a search on an attribute needs the full name with the prefix, and the field browser in Discover shows the full name. These field names are real, from the demo index.

Step 1 of 9

Install the C compiler, the PHP header files and pecl

To install the OpenTelemetry PHP extension, the server needs the PHP header files, the pecl command and a C compiler. The package php-pear provides the pecl command.

Ubuntu 24.04 LTS

apt install php8.3-dev php-pear \
            gcc make autoconf

RHEL 9 · Rocky 9

dnf install php-devel php-pear \
            gcc make autoconf
Walk-through
~1 min. Checked on both distributions, not read in a blog. PHP itself is not installed here: anyone running Moodle 5.2 already has PHP 8.3 and PHP-FPM, so only the packages this extension needs are added. php-pear is what provides the pecl command on both — without it the next slide fails at "command not found". The header package (php8.3-dev, php-devel) and the compiler packages are needed because the extension is built from source. On RHEL and Rocky, php-devel comes from the enabled module stream, so it matches the PHP that Moodle runs on.

Step 2 of 9

Install and enable the OpenTelemetry PHP extension

PECL is the PHP site that publishes extensions. The command pecl install opentelemetry downloads the extension and builds the file opentelemetry.so for the PHP version on your server. A small php.ini file then tells PHP to load it.

Ubuntu 24.04 LTS

pecl install opentelemetry   # compiles the C source with gcc

echo "extension=opentelemetry.so" \
 > /etc/php/8.3/mods-available/opentelemetry.ini

phpenmod opentelemetry
systemctl restart php8.3-fpm

RHEL 9 · Rocky 9

pecl install opentelemetry   # same: compiles with gcc

echo "extension=opentelemetry.so" \
 > /etc/php.d/40-opentelemetry.ini

# no phpenmod — the drop-in is enough
systemctl restart php-fpm

Run php --ri opentelemetry to check the result. The output must contain opentelemetry hooks => enabled.

Walk-through
~1 min 30 s. Two differences worth naming out loud. Debian and Ubuntu split configuration into mods-available plus a phpenmod symlink per SAPI; Red Hat just drops a numbered file into /etc/php.d and is done. The number 40 controls load order and matters only if an extension depends on another — 40 is a safe middle. pecl install compiles, so it takes a minute and needs the compiler from the previous slide. If they have never used PECL or PHP Composer, say that is normal — they are PHP developers' tools, not sysadmin ones — and that extension is not package: the extension is C, from PECL, listed in php.ini; the packages on the next slide are PHP, from PHP Composer, listed in composer.json. Different tools, different files, both needed. And the restart is not optional: the CLI picks the extension up immediately, FPM does not.

Step 3 of 9

Install PHP Composer and the two OpenTelemetry PHP packages

The OpenTelemetry PHP code comes as two packages. PHP Composer is the tool that downloads PHP packages. Install PHP Composer first.

Ubuntu 24.04 LTS

# packaged, version 2.7
apt install composer

RHEL 9 · Rocky 9

# not in AppStream — use the installer
curl -sS https://getcomposer.org/installer \
  | php
mv composer.phar /usr/local/bin/composer

Then run these two commands in the Moodle folder. They are the same on Ubuntu and on Red Hat. Each command downloads one package into the folder /var/www/moodle/vendor/.

cd /var/www/moodle
composer require moodlehq/moodle-package-otel   # records the Moodle events and timings
composer require open-telemetry/exporter-otlp   # sends the records to the OpenTelemetry Collector
Walk-through
~1 min 30 s. Say whose dependency this is before anyone asks: Moodle does not need Composer — the OpenTelemetry PHP libraries do, because Composer is the only way they are shipped. You run it once, against the Moodle directory, so the libraries land where Moodle 5.2 will load them. Then walk the two packages against the chain: moodle-package-otel is component 3, written by Moodle HQ — it knows Moodle from the inside, which methods to time and which events to forward. exporter-otlp is component 4, from the OpenTelemetry project — it packs spans and log records into OTLP messages and sends them to the collector, and Composer pulls the OpenTelemetry SDK in as its dependency. Neither does anything yet: the switch is the environment variables, two steps ahead. Checked: Ubuntu 24.04 packages Composer 2.7.1; Rocky and RHEL 9 do not package it at all, so the official installer is the normal route there. Reassure the room that this writes only into vendor/ and never touches Moodle core — for many this is their first time running Composer against a production Moodle. Run it as the user that owns the Moodle tree, not as root, or the web server cannot read what it wrote. The 5.2 line is verified in both source trees: 5.1 has it at public/lib/setuplib.php:82 inside the Whoops handler, which returns early for CLI, for AJAX, and whenever debugdisplay is off. Anyone on 5.0 or 5.1 now knows why the answer is "upgrade first" — one line, not a rewrite. If anyone asks why 5.2 is the minimum: one line in public/lib/classes/component.php loads vendor/autoload.php on every request; Moodle 5.1 has it only inside its error handler.

Step 4 of 9

Six environment variables configure the OpenTelemetry PHP libraries

The OpenTelemetry PHP code reads its settings from environment variables of the PHP process. These are the six.

OTEL_PHP_AUTOLOAD_ENABLED=true                             # switches the OpenTelemetry PHP code on
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318          # the address of the OpenTelemetry Collector
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf                  # the data format on the network
OTEL_TRACES_EXPORTER=otlp                                  # sends the timings
OTEL_LOGS_EXPORTER=otlp                                    # sends the events
OTEL_METRICS_EXPORTER=none                                 # sends no metrics

Moodle has no setting for these variables. They do not go into config.php, and the Moodle admin pages do not show them.

Walk-through
~1 min 30 s. Every one is a standard OpenTelemetry PHP variable, not a Moodle invention, so the reference for them is https://opentelemetry.io rather than moodledev. AUTOLOAD_ENABLED is the on switch and the silent failure: without it nothing runs and nothing complains. Say where they go before anyone asks: the environment of the PHP process, which means three files, one per way PHP starts, on the next slide. Say also what they are NOT — not config.php, not a database setting, not an admin page — because someone will otherwise spend an afternoon hunting the Moodle admin tree. The protocol line: http/protobuf means HTTP on port 4318. gRPC on port 4317 also works, but it needs one more PHP Composer package.

Step 5 of 9

Write the six environment variables into two files

Moodle runs PHP in two places that matter here. PHP-FPM runs it for web requests, and cron runs it for the scheduled tasks. Each has its own environment, so the same six lines go into two files.

1 · For web requests, add the lines to the PHP-FPM pool file.
Ubuntu /etc/php/8.3/fpm/pool.d/www.conf  ·  RHEL /etc/php-fpm.d/www.conf

env[OTEL_PHP_AUTOLOAD_ENABLED] = true
env[OTEL_EXPORTER_OTLP_ENDPOINT] = http://localhost:4318
# add one env[] line for each of the six variables, then restart PHP-FPM

2 · For Moodle cron, add the lines to the cron file that you already have, above the schedule line.
/etc/cron.d/moodle

OTEL_PHP_AUTOLOAD_ENABLED=true
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
* * * * * www-data php /var/www/moodle/admin/cli/cron.php >/dev/null   # RHEL: apache
Walk-through
~2 min. The slide people will photograph. Three points. One: PHP-FPM does not inherit your shell — the pool file is the only thing it reads, and the syntax is env[NAME] = value, not export. Two: cron is the same Moodle cron entry that already exists; crontab files accept plain NAME=value lines above the schedule, so you edit the file you already have. If they run Moodle cron from a systemd timer instead, the equivalent is Environment= or EnvironmentFile= in the unit. Three: a hand-run CLI command gets nothing unless the variables are in that shell, which is what the profile.d file fixes — or prefix the one command. Symptom of missing one: web traces but no cron traces, or the reverse, and never an error message.

Step 6 of 9

Configure OpenSearch

OpenSearch needs four things before the first records arrive.

WhatWhere you do itWhy
A user for the OpenTelemetry Collector OpenSearch Dashboards, Security, Internal users and Roles The OpenTelemetry Collector logs in as this user. The role needs create_index and write on otel-v1-logs-* and otel-v1-apm-span-*, and the cluster permissions cluster_manage_index_templates and indices:data/write/bulk.
An index template You do nothing. The OpenTelemetry Collector creates it at start. The template sets the field types of each new monthly index. It needs OpenTelemetry Collector 0.157.0 or newer.
An index pattern Dashboards Management, Index patterns, Create. The pattern is otel-v1-logs-* and the time field is time. Discover is the search page of OpenSearch Dashboards. It shows no data without the pattern.
A retention policy Index Management, State management policies, Create policy, with an ISM template for otel-v1-logs-* and otel-v1-apm-span-* ISM (Index State Management) deletes old indices on a schedule. The policy covers only the indices that come after it.
Walk-through
~1 min 30 s. This is the slide the OpenSearch administrator in the room has been waiting for, and the one the Moodle administrator will hand to a colleague. Say the split out loud: the collector is yours, the four rows here are done by whoever runs OpenSearch. Row one: the action group names are OpenSearch's own — write means create and update documents in existing indices, create_index means create indices and mappings, and the cluster-level cluster_manage_index_templates is what manage_index_template needs, and the cluster-level indices:data/write/bulk lets the collector send its records in bulk. Without it OpenSearch answers 403 to every batch; a fresh demo stack showed this on 2026-09-23. Row two: the exporter README says manage_index_template "creates composable index templates on startup" and is only valid with otel-v1 mode; the version numbers are from the collector changelog. Row three: the demo stack's README has this exact step, and creating the pattern through the API instead of the screen gives a pattern without a field list that Discover rejects. Row four: the ISM documentation says the policy is attached "when an index that matches the ISM template pattern is created" — so create the policy before the first monthly index, or attach it by hand. Moved off the slide: the security plugin is part of every OpenSearch install and is on unless someone switched it off; the collector logs in with a basicauth extension, an https endpoint and a tls setting, shown in step 8; mode: otel-v1 arrived in collector 0.154.0 and manage_index_template in 0.157.0, and older builds such as 0.144.0 have neither key.

Step 7 of 9

Install the OpenTelemetry Collector

The OpenTelemetry Collector runs as a service. It receives the records from Moodle and sends them to OpenSearch. These steps install it on the Moodle server, and it can also run on its own host. It is not in the standard Ubuntu and Red Hat repositories, so you download the .deb or .rpm package from GitHub. The releases page on GitHub shows the newest version.

Ubuntu 24.04 LTS

RHEL 9 · Rocky 9

Walk-through
~1 min. Say why the version is pinned in a variable: the collector releases every few weeks and the config keys change between versions — you will see a concrete example on the next slide. Take contrib, not the core build: the OpenSearch exporter only exists in contrib. After installing, the service is enabled but the shipped config does nothing useful until the next slide replaces it. Checked in the 0.159.0 package files: the postinstall script enables and starts the service at once, with the ready-made config file. That file listens on 0.0.0.0 on ports 4318 and 4317 (OTLP), 14250, 14268, 6831 and 6832 (Jaeger) and 9411 (Zipkin), and its debug exporter writes every record in full to the system log. Step 8 replaces the whole content of the file, and that closes the extra ports. Say this aloud; it is not on the slide. Also say that the Collector is the only new service. The PHP extension and the PHP packages run inside PHP, so after a change to them you restart PHP-FPM, and after a change to the Collector configuration you run systemctl restart otelcol-contrib.

Step 8 of 9

Configure the OpenTelemetry Collector to receive the records

The PHP package exporter-otlp sends the records from Moodle to http://localhost:4318. In the file /etc/otelcol-contrib/config.yaml, you configure the OpenTelemetry Collector to listen on that port.

receivers:    # listens on port 4318 for the records from the PHP package
  otlp:
    protocols:
      http:
        endpoint: localhost:4318
processors:   # sends the records in groups, one group every 5 seconds
  batch:
    timeout: 5s
Walk-through
~45 s. The file is one file, shown on two slides so the text stays readable. This half takes the records in. The sender is the PHP package exporter-otlp inside PHP. receivers opens port 4318, the OTLP port that the variable OTEL_EXPORTER_OTLP_ENDPOINT from step 4 points at; localhost because the OpenTelemetry Collector runs on the Moodle web server, so the port stays closed to the network. A shared collector on its own host needs 0.0.0.0 here and a firewall rule. processors: batch groups records for five seconds before they are sent, so one busy Moodle does not open a connection per event. The demo file has one more processor, transform/cli-status, that fixes the cron timings. The README of the demo explains it. It is not on the slide on purpose.

Step 8 of 9

Configure the OpenTelemetry Collector to send the records to OpenSearch

The OpenTelemetry Collector needs the login, the address of OpenSearch and the names of the indices.

extensions:   # the user name and the password for OpenSearch
  basicauth/opensearch:
    client_auth:
      username: otelcol
      password: DemoCollector2026!
exporters:   # sends the records to OpenSearch
  opensearch/moodle:
    http:
      endpoint: https://opensearch1:9200   # the address of your OpenSearch server
      auth:
        authenticator: basicauth/opensearch
      tls:
        insecure_skip_verify: true   # does not check the certificate of OpenSearch
    logs_index: "otel-v1-logs-moodle"   # the name must start with otel-v1-logs
    logs_index_time_format: "yyyy.MM"   # one new index each month
    traces_index: "otel-v1-apm-span"   # the trace pages read this name, keep it
    traces_index_time_format: "yyyy.MM"
    mapping:
      mode: "otel-v1"
      manage_index_template: true   # creates the index template at start
service:   # nothing runs without this section, it switches the parts on
  extensions: [basicauth/opensearch]
  pipelines:
    logs: {receivers: [otlp], processors: [batch], exporters: [opensearch/moodle]}
    traces: {receivers: [otlp], processors: [batch], exporters: [opensearch/moodle]}

Restart the service with systemctl restart otelcol-contrib. The OpenTelemetry Collector reads the file only at start.

Walk-through
~1 min 30 s. Say the host name out loud: opensearch1 is our name for the OpenSearch server in this and every following example, including the curl on the next slide — they substitute theirs. extensions holds the user name and the password of the OpenSearch user from step 6; the exporter points at this block by name and does not carry the credentials itself. insecure_skip_verify: true switches off every check of the OpenSearch certificate; with a real certificate, remove the line or set ca_file. The part after that is yours to name, and one events index per site is a sane default; Discover finds it by pattern. mapping.mode: otel-v1 writes one field layout for both kinds of data. Plan for personal data in the events and for too many indices

Cautions
Section runs ~3 min 30 s. Credibility section. This audience trusts a talk more when the speaker names the downsides before they do.

Caution 1

Events can carry personal data

  • By default an event identifies a user only by id, for example "the user with id '2'". A failed login also records the user name that was typed.
  • Every email that Moodle fails to send is stored as an email_failed event, with the full text of the email. Moodle's own new-device sign-in notice is such an email, and it contains the user's name, email address, IP address and browser.
  • The index holds personal data as soon as one record identifies a person. The General Data Protection Regulation (GDPR) then applies to the index, not only to Moodle.
  • Remove or hash such attributes in the OpenTelemetry Collector, before they reach OpenSearch. For example, this statement in a transform processor deletes the email text:
delete_key(log.attributes, "event.data.other")
  where log.attributes["event.data.eventname"] == "\\core\\event\\email_failed"
  • Decide the retention period before you switch the sending on.
Cautions
~2 min. For a Swedish education host this is an important point. It decides whether the whole thing gets approved. The email_failed example is real and verified on the demo stack: the event's other.message attribute held the full text of a sign-in notification, including the account email, the login IP and the user agent. Tell what happened, step by step. It is the single most convincing argument for filtering in the collector: one config, off the Moodle components, applied to every site at once. The pseudonymity point has two sides: good for privacy by default, and it means dashboards show ids unless you deliberately enrich them.

Caution 2

OpenSearch stores every index in shards, and a server has a limit on shards

An index in OpenSearch is stored on disk as one or more pieces called shards. By default one data server accepts at most 1000 shards, and every new index brings the server closer to that limit.

What happens without a retention policy

By default each index has two shards, one primary and one copy. For example, five daily indices add ten shards per day, and they reach 1000 shards in 100 days. From then on OpenSearch cannot create the new day's indices, and it rejects every incoming record. Nothing alerts you by default.

  • Very large shards are also a problem. The OpenSearch documentation recommends 10 to 50 GB per shard. Above that, searches slow down.
  • Choose the index period so that one index stays in that range. One index per month, logs_index_time_format: "yyyy.MM" in the OpenTelemetry Collector's configuration file, fits a site that writes up to a few million events a day.
  • Create the retention policy in OpenSearch on the first day, so old indices are deleted and their shards are freed.
Cautions
~1 min 30 s. The 1000 is the default of cluster.max_shards_per_node; it can be raised, but that only postpones the problem. The card is arithmetic, not a story: five daily indices reach 1000 shards after 100 days, because the limit counts the primary and the replica. The sizing sentence comes from the demo index, about 290 bytes per event record on disk, so one million events a day is about 9 GB a month. Weekly indices are not available: the exporter's index name format knows only yyyy, yy, MM, dd, HH, mm and ss. If asked, the OpenSearch-native way to get a fixed index size is an ISM rollover policy behind an alias.

Moodle also sends timing data to OpenSearch through the same OpenTelemetry Collector

Timing data
Section runs ~3 min 30 s. The cautions are over. Two slides on the timing data, then the demo. Say once, out loud: the timing data goes through the same OpenTelemetry Collector into the same OpenSearch. Nothing new is installed for it. The collector file from step 8 already has the pipeline named traces.

Timing data

Every request also records how long each of its steps took

Every event record has two fields called traceId and spanId. They are there because the request that wrote the event also recorded how long each of its steps took. OpenTelemetry calls the timing of one request a trace. A trace is made of spans. A span is one step of the request, with a start time and a duration.

Timing data
~2 min. Everything so far was events. Point at the traceId and say it has been on every document shown this hour. Two new words, define each one in a short sentence: a trace is one request's timing record start to finish, a span is one step inside it. Correct the common wrong guess out loud: a trace does not follow a user around; it ends when the request ends, and a cron run is a trace too. Then read the picture: a real login request from the demo site took 92.8 ms, and the login event inside it took 2.5 ms. The trace id is 37a0a4f13ade731c02fb88010eb876b4, and the event record "The user with id '2' has logged in." carries the same traceId. No span covers the 79 ms before the login event, so the trace does not name the slow step. The first span carries a note named moodle.shutdown_handler with Moodle's own summary of the request: dbtime 0.032 s, dbqueries 13/9, which is 13 reads and 9 writes. This is the fifth question from the opening, answered in part, by the same OpenTelemetry Collector that ships the events.

Timing data

The timing data shows where Moodle spends its time

It answers these questions.

  • Which pages are slow, and how slow?
  • Which scheduled task ran for 40 minutes last night?
  • How long did each Moodle event take inside a request?

A span has attributes, the same as an event. So you search spans the way you search events, and you can sort them by duration.

In OpenSearch Dashboards this data is usually viewed under Observability.

Timing data
~1 min 30 s. Say it once, plainly: nothing extra was installed for this. The events and the timing data use one collector and one store, the same collector file as the walk-through. Close with the promise: the timing data gets its own session. Only if asked: by default the Trace analytics page reads spans from indices named otel-v1-apm-span-*, so the OpenTelemetry Collector writes the spans under that name, with its traces_index setting. With another name the spans are stored, but the page stays empty until you change the setting observability:traceAnalyticsSpanIndices in OpenSearch Dashboards. Only if asked: two views on the Trace analytics page, Services and the service map, need a second index. Only Data Prepper builds it. Data Prepper is a separate OpenSearch program that sits between the OpenTelemetry Collector and OpenSearch. Only if asked: a sampling rate of 10 % is a starting convention, not a Moodle measurement, and OTEL_SERVICE_NAME does not reach the stored span, verified on a real one.
